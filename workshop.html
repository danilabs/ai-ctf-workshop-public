What you will build today

A harness of your own on top of OpenCode, in four phases.

1 · Understand

What an agent is, what a harness is, and which parts OpenCode already gives you.

2 · Prepare

OpenCode V2 installed, a model configured, and a practice challenge.

Block 1

From chatbot to agent

Tools, the loop and ReAct · 10 minutes

Block 1 · Agent

A chatbot talks, but does not act

You↓LLM↓Answer

It cannot see your challenge

It only knows what you paste into the chat.

It cannot run anything

It can suggest strings, but it cannot run it.

It starts from zero

Each conversation forgets the previous one.

An LLM predicts text. Without tools it can only talk. Example: you paste a snippet from a challenge and it explains the vulnerability, but it cannot open the binary. The first fix is to give it hands.
Block 1 · Agent

Tool calling: the model asks, the system runs

You ask: "Which readable strings does challenge.bin contain?"

// 1. The model produces a structured call
{ "tool": "shell", "args": { "command": "strings challenge.bin" } }

// 2. The system runs the tool and returns the output
admin_panel_v2  /api/login  debug=true

// 3. The model answers from that output
There is a /api/login endpoint and a debug flag enabled.

Illustrative example.

The model never executes anything. It writes a structured request, and the harness executes it. Like a waiter taking your order to the kitchen. One call is not enough: an agent needs to repeat this, which is the next slide.
Block 1 · Agent

The loop turns tool calling into an agent

Without a loop

You↓LLM↓Tool call↓Result → answer

One action. Done.

With a loop (agent)

You↓LLM↓Tool call↓Result → back to the LLM↓Done yet?

Repeats until the goal is met or the step limit stops it.

The difference between a single tool call and an agent is the loop. The model sees each result and decides the next step. Example: it runs file, sees an ELF, decides to run strings, sees a path, and decides to open that file.
Block 1 · Agent

Agent = LLM + tools + loop + context

A system that interprets a goal, decides actions, uses tools, observes results and keeps going until the goal is reached.

Autonomous

It decides each step without being told.

Goal-directed

It works toward a result, not just an answer.

Iterative

It repeats until done or stopped.

Four ingredients. The keyword is "keeps going". "Find the flag" is a goal; "run strings" is a command. In OpenCode, the loop, the base tools and the session are provided. Context and the rules are what you build.
Block 1 · Agent

ReAct: think, act, observe

Thought

The model reasons about the next step.

Action

It picks a tool and calls it with parameters.

Observation

It reads the result and decides whether it is done.

Thought:     This is a binary. Let me check the file type.
Action:      shell → file challenge.bin
Observation: ELF 64-bit, not stripped
ReAct (Yao et al., 2022) interleaves reasoning and acting. Each turn adds new information. "Not stripped" suggests function names will be available, which changes the next move.
Block 1 · Agent

Agent vs workflow

Workflow

step A → step B → step C → step D

Fixed path, always the same.

Agent

goal → decide → A or B → observe → decide again

The path depends on what it finds.

A workflow is predictable and cheap; an agent is flexible and harder to control. CTF challenges differ from each other, which is why an agent is useful. In practice most harnesses mix both: a fixed workflow for the boring setup, an agent for the decisions.
Block 1 · Agent
Quick question1 min

A script always runs file, strings and checksec, in that order. Agent or workflow?

Workflow. The order is fixed and nothing decides anything. If the script chose the next tool based on the output, it would be an agent.
Expected answer: workflow. Follow-up: what would you add to turn it into an agent? A model that decides, and a loop.

Block 2 · Harness

Without a harness, an agent breaks

No memory

Repeats the same work every session.

→ persistence

No guardrails

Runs dangerous commands without stopping.

→ permissions

No observability

A black box: you cannot see what it did.

→ hooks, logs

No error handling

One failing tool and everything stops.

→ step limits

No permissions

Any tool, at any time.

→ allow / ask / deny

No context control

The window fills and the important part is lost.

→ AGENTS.md, skills

No oversight

Decides critical things alone.

→ approvals

No validation

Invents tools or parameters.

→ tool schemas

An LLM plus tools plus a loop sounds powerful, but in practice it fails in these eight ways. Each one has a piece in the harness. Example: without a step limit, an agent stuck on the same command keeps spending tokens.
Block 2 · Harness

Brain and body

A brain cannot do anything on its own. It needs a body.

LLM = brain

Reasons, decides, plans.

It cannot reach the internet, run code, remember anything between sessions, or verify its own output.

Harness = body

Everything needed to act in the real world.

Tools = hands · Context = memory · Permissions and guards = reflexes · Hooks and logs = self-awareness

Reflexes pull your hand off a hot pan without thinking. Guardrails stop rm -rf without asking the model. The analogy helps remember the map.

A command is a prompt template: it costs nothing until you use it, and $ARGUMENTS receives what you type after it. A skill is different: only its name and description sit in the context. Step 4 · Permissions and policies

0 Setup1 Scope2 Agent3 Command4 Permissions5 Subagent6 Plugins7 Verify
"permissions": [
  { "action": "*",     "resource": "*",         "effect": "allow" },
  { "action": "shell", "resource": "sudo *",    "effect": "deny"  },
  { "action": "shell", "resource": "rm -rf *",  "effect": "deny"  },
  { "action": "read",  "resource": "*.env",     "effect": "ask"   }
],
"policies": [
  { "action": "tool.use", "resource": "read:*/.ssh/*", "effect": "deny" }
]

allow

Runs without asking.

ask

Waits for your approval.

deny

Blocked every time.

Rules are evaluated in order and the last matching rule wins. With no match, the default is ask. Policies never prompt and cannot be overridden by "allow always". Agent-level rules are appended after the global ones, so a broad allow inside an agent re-enables what the global config denies. Never write one.

Step 6 · A guard plugin

0 Setup1 Scope2 Agent3 Command4 Permissions5 Subagent6 Plugins7 Verify
// .opencode/plugins/guard/index.ts
import { Plugin } from "@opencode/plugin"

export default Plugin.define({
  id: "mi-harness.guard",
  async setup(ctx) {
    const root = ctx.location.directory   // the folder you started in
    await ctx.permission.hook("evaluate", async (event) => {
      if (event.action !== "edit") return
      for (const r of event.resources) {
        const t = r.startsWith("/") ? r : `${root}/${r}`
        if (!t.startsWith(`${root}/`) || t.startsWith(`${root}/files/`)) {
          event.effect = "deny"
          event.message = "Writes stay in this folder; files/ is read-only."
        }
      }
    })
  },
})

Known gap, on purpose

This version does not normalize .., so work/../../x slips through. Your offline test must catch it.

A rule in prose is advice. A permission hook is a check. The reference implementation in .opencode/plugins/challenge-guard/index.ts normalizes paths before comparing; the offline test in .opencode/scripts/test-challenge-guard.mjs shows the deny and allow matrix. Write the test first, watch it fail, then fix.

Step 6 · A tool and a hook

0 Setup1 Scope2 Agent3 Command4 Permissions5 Subagent6 Plugins7 Verify

A tool (ctx.tool.transform)

await ctx.tool.transform((editor) => {
  editor.add({
    name: "flagcheck",
    description: "Check a flag against the
      event format, without submitting it",
    input: {
      type: "object",
      properties: { flag: { type: "string" } },
      required: ["flag"],
      additionalProperties: false,
    },
    execute: async ({ flag }) => ({
      content: /^[A-Za-z0-9_]+\{[^}]+\}$/.test(flag)
        ? `looks valid: ${flag}`
        : "does not match a common flag format",
    }),
  })
})

A hook (ctx.tool.hook)

import { appendFileSync } from "node:fs"

ctx.tool.hook("execute.before", async (event) => {
  appendFileSync(`${root}/work/trace.jsonl`,
    JSON.stringify({ at: Date.now(), event }) + "\n")
})

Payload fields differ between versions. Log the whole event first, then read the fields you need.

Plugins register tools (ctx.tool.transform), hooks on tool calls (ctx.tool.hook with execute.before and execute.after), session hooks (ctx.session.hook with context, compaction, generate) and permission hooks (ctx.permission.hook with evaluate). The context hook receives the request, including the tool list, so it can change what the model sees on each call. Plugin tools get their own permission action, so you can deny them like any other.

The 8 principles of a good harness

  1. Tools that fit the work
  2. Reliable tools that behave the same way every time
  3. Least privilege in permissions
  4. Good context management
  5. Observability of every action
  6. Human approval for risky actions
  7. Failure handling at every level
  8. Evaluation, to measure and improve
Each principle maps to something you built today. Least privilege: the recon permissions. Context: a short AGENTS.md and on-demand skills. Evaluation: the test table.
